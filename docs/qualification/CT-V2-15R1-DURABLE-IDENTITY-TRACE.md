1. **Definitions/domain.** ProductionTurnRequest.clientTurnIndex is a positive Long. ThomasProductionRuntime.identity makes `android-{journal|biographer|therapy}-{index}`. The Android application shares one numeric sequence across modes and lifecycle commands within its protected corpus. Render command identities are `android.{kind}.{index}`; they do not grant persistence authority. Reset/replacement restore follows the existing corpus replacement contract, not a global account/device identity contract.
2. **Allocation.** ThomasViewModel initializes nextTurnIndex from runtime.snapshot().storeRevision + 1, repeats that initialization after reset, and increments in synchronized allocateTurnIndex. This was introduced as the Android composition convention; there is no store contract equating revisions with turn indexes.
3. **All production callers.** ViewModel.submit (all three modes), requestBiographerPrompt, reviseSource, and performSourceLifecycle (changeSourcePrivacy/deleteSource) call allocateTurnIndex. nextBiographerPrompt consumes an index without admitting a user source. Runtime also renders the next Biographer prompt at clientTurnIndex + 1; this does not commit another turn. Qualification callers supply explicit indexes but are not additional production allocators.
4. **Persistence.** ProductionJournalPipeline, ProductionBiographerPipeline and ProductionTherapyPipeline turn mode-specific identities into admission idempotency keys. Lifecycle/revision methods in ThomasProductionRuntime create `android-lifecycle-{action}-{index}` and `android-source-revision-{index}` keys. ProtectedPersonalDataStoreImpl.submit fingerprints requests, strictly rejects conflicting existing keys, and atomically writes the authenticated document containing ledger events, receipts and projection. Revisions count accepted mutations, including language evidence and lifecycle operations; prompts need not produce any mutation.
5. **Reconstruction.** ThomasAndroidCompositionRoot.open/openRuntime constructs AndroidPersonalDataPersistenceFactory's protected store and a new ThomasProductionRuntime. The factory authenticates/decrypts the primary artifact; PersonalDataDocumentCodec.decodeAndVerify reconstructs the projection from checkpoint and ledger. Activity ViewModel recreation/process restart creates the allocator anew. Backup replacement also creates a new runtime. An activity configuration recreation normally retains its ViewModel.
6. **Durable frontier.** LongitudinalReader.redactedAdmissionHistory returns both archived and active accepted request/key identities. Deletion erases source content through a checkpoint but retains redacted ledger headers and collision receipts. Therefore current source count or maximum current source ID alone is insufficient. The existing redacted reader supplies the required durable identity information without exposing deleted content or changing persistence.
7. **Repair boundary.** Move allocation into the runtime that owns the current protected store, derive the maximum canonical allocated numeric suffix from durable admission keys, and combine it with the current runtime's allocated frontier. All ViewModel callers delegate there, so restored/replaced runtime state is used automatically. Use checked increment to prevent numeric wraparound. Preserve explicit submit indexes/idempotent caller behavior and unchanged store conflict guards.
8. **Compatibility.** Existing schema and keys already contain the information needed, including archived deletion history and migrated v1 ledger events. No schema migration, renumbering, history rewrite or storage change is needed. Empty corpus starts at 1. Uncommitted allocations need only remain distinct during the runtime lifetime; after restart allocation must exceed every prior committed canonical index. The existing single application runtime/store writer contract is retained; this is not a new multiprocess allocator architecture.

Failure-first regression will commit multiple turns around an unrecorded prompt, close/reconstruct the protected file store, use the starting ViewModel formula, record actual revisions/indexes, submit a conflicting new payload, and assert both admission and exact identity progression. The historical diagnostic remains unchanged as an independent strict collision-defense test.
